# VideoBrowser 1.11.6 – Stage 3.6 (xHamster frame extraction and diagnostics)

- Version Name: `1.11.6`
- Version Code: `20`
- الهدف: معالجة تقرير xHamster الذي أظهر Blob/MSE مع صفر إعدادات مشغّل/مصادر، وتحسين تشخيص صيغ HLS التي يرفضها فلتر المدة.

## ما تغير

1. قراءة بنية المشغّل المعلنة `initials.videoModel.sources` و`initials.xplayerSettings.sources` في الصفحة الرئيسية والإطارات التي تحتوي الفيديو.
2. التقاط روابط HTTP(S) الواضحة فقط، مع الاحتفاظ ببيانات الجودة/الترميز/الدقة عندما تكون معلنة داخل بنية المشغّل.
3. تجاهل مفاتيح download والإعلانات والمعاينات. القيم المعتمة/المشفرة تُحصى للتشخيص فقط ولا يتم فكها أو تحويلها.
4. تمرير عدد مصادر xHamster والجودات المعلنة والقيم المعتمة من iframe إلى التشخيص الأصلي.
5. منع عرض مصادر xHamster المعلنة أثناء preroll المصنّف، ثم استعادتها عند انتقال عنصر الفيديو إلى المحتوى.
6. تجاهل قوائم Resource Timing التي سبق تحميلها قبل حد الانتقال من الإعلان إلى المحتوى داخل iframe، مع السماح بالقوائم الحديثة التي تُحمّل بعد الانتقال.
7. عند رفض Content Filter لصيغة بسبب اختلاف المدة، يُظهر التشخيص المضيف ومصدر الالتقاط والمدة المكتشفة مقابل مدة المشغّل بدل الاكتفاء بعدّاد الرفض.

## حدود معروفة

- لا يتم فك قيم `xplayerSettings` المعتمة أو محاولة تحويلها إلى روابط. إذا لم يعرض الموقع رابطًا واضحًا أو قائمة HLS/DASH يمكن قراءتها، سيظل المصدر غير قابل للاستخدام في هذه المرحلة.
- لا نرفع الجودة اصطناعيًا إلى 2K/4K. تظهر هذه الدقة فقط إذا كشفت بيانات المشغّل أو القائمة عن تمثيل حقيقي بهذه الدقة.
- لا يثبت اختبار المصدر أن كل فيديو في xHamster يوفّر 2K؛ ذلك يعتمد على تمثيلات كل فيديو وما يسمح الموقع بعرضه في الجلسة.
- لم يُنفذ Android `assembleDebug` في بيئة إعداد الحزمة لعدم توفر Android SDK/Gradle. يلزم تأكيد البناء عبر GitHub Actions قبل التثبيت.

## الاختبارات المحلية المنفذة

- 11 اختبار JavaScript: التقاط المصادر، API/JSON، HLS، جودة player config، document-start، iframe، Shadow DOM، preroll، invariants، واستخراج xHamster في الصفحة الرئيسية والإطار.
- 5 مجموعات Kotlin: HLS master، resolver، metadata، capture headers، signed URL expiry.
- اختبار NetProbe fallback: Range 410 ثم GET header-only، مع بقاء 410 الحقيقي مرفوضًا.
- تحقق من تجميع `ApiCaptureScript.kt` عبر Kotlin compiler.
- لم يتغير `DownloadCenter.kt` أو `Hls.kt` عن المصدر 1.11.5.1.

تفاصيل تشغيل الاختبارات: `tools/quality-tests/README_AR.md`.

# VideoBrowser 1.11.5 – Stage 3.5

تصحيح مرحلة فحص مصادر المشغل التي عادت HTTP 410.

- التقاط سياق الطلبات ذات الروابط غير النمطية التي أعلنها المشغل صراحة، دون تحويل نقاط API العامة إلى صيغ تنزيل.
- ربط ترويسات الطلب الآمنة بالرابط المطابق حرفيًا فقط، مع التحقق من حداثة السياق وأصل إطار الفيديو.
- عدم إعادة استخدام سياق طلب تم التقاطه أثناء الإعلان لتمثيل المحتوى بعد الانتقال.
- عند رفض CDN لفحص Range، يجرب التطبيق HEAD ثم GET دون Range لقراءة ترويسات الاستجابة فقط؛ لا ينزل جسم الفيديو أثناء الفحص.
- إذا أعاد الخادم 410 حتى مع الطلب العادي، يبقى المصدر مرفوضًا ويظهر التشخيص أن الرابط غير متاح حتى بعد فحص Range/HEAD/GET. لا يحاول التطبيق توليد رابط أو تخطي انتهاء صلاحيته.

لم يتغير DownloadCenter.kt أو Hls.kt عن الإصدار 1.11.3.

## Stage 3.5 – preroll and fresh manifest recovery

- منع فتح قائمة التنزيل أثناء الإعلان أو المصدر التمهيدي.
- تصنيف preroll عند اختلاف مدة عنصر الفيديو بوضوح عن مدة المحتوى المعلنة في flashvars، مع المحافظة على الفيديوهات القصيرة الحقيقية.
- التقاط قوائم HLS/DASH الحديثة التي ظهرت في Resource Timing دون قراءة أجسام المقاطع.
- التقاط سياق طلبات WebView للصفحة الرئيسية والإطارات معًا.
- كشف انتهاء روابط signed URL المعروفة عبر validto/expires قبل محاولة الفحص.
- توضيح HTTP 410 على أنه رابط لم يعد متاحًا بدل محاولة عرضه كخيار تنزيل.

لم يتم تغيير DownloadCenter.kt أو Hls.kt. لم يُبنَ APK كامل في بيئة إعداد المصدر؛ يلزم تشغيل assembleDebug في GitHub Actions ثم اختبار الموقع فعليًا.


## Stage 3.5 – نتائج تشخيص 410 والإعلانات

- إعطاء الأولوية لقوائم HLS/DASH التي رصدها المشغل فعليًا في Resource Timing قبل روابط Flashvars المباشرة التي قد تكون قديمة.
- توسيع التقاط سياق طلبات GET إلى الصفحة الرئيسية والإطارات، مع الاحتفاظ بالترويسات الآمنة فقط.
- منع الزر من التحول للأحمر أثناء إعلان أو مصدر تمهيدي تم التعرف عليه، ومنع فتح خيارات تنزيل الإعلان.
- تمرير سبب تصنيف الإعلان ومدة المحتوى من iframe إلى تشخيص Kotlin، وإزالة حالة الإعلان القديمة عند انتقال نفس عنصر الفيديو إلى المحتوى.
- اكتشاف روابط signed URL المنتهية المعروفة عبر validto/expires دون طباعة قيمها في التشخيص.

لم يتغير DownloadCenter.kt أو Hls.kt. لم يُبنَ APK كامل في هذه البيئة؛ يلزم تشغيل assembleDebug في GitHub Actions ثم التحقق على الجهاز.


## الإصدار 1.11.8 — التقاط صيغ المحتوى أثناء الإعلان وإصلاح إعادة المحاولة

- أصبح التطبيق يحتفظ بصيغ المحتوى التي يعلنها المشغل صراحة في `mediaDefinitions` أو `initials` حتى لو كان عنصر الفيديو يعرض إعلانًا تمهيديًا.
- لا نحتفظ بـ`currentSrc` الخاص بالإعلان، ولا بروابط الإعلان/المعاينة الصريحة. كما تبقى قوائم Resource Timing القديمة مخفية أثناء الإعلان إلى أن يحدث انتقال المحتوى.
- أصبح الزر العائم أحمر أثناء الإعلان فقط عندما يكون المستخدم قد بدأ التشغيل وكانت صيغ المحتوى الأصلية قد رُصدت؛ ويمكن الضغط عليه لعرض صيغ المحتوى، وليس الإعلان.
- حصر Resolver أثناء الإعلان على مصادر المشغل المعلنة صراحة، مع الاستفادة من مدة المحتوى التي كشفها المشغل للتحقق من أن الصيغ تخص الفيلم.
- إصلاح التخزين السلبي لنتيجة صفر صيغ: الضغط اليدوي مرة أخرى يسمح بإعادة تحليل مصادر WebView وإعادة محاولة yt-dlp، بدل تكرار رسالة الفشل دون محاولة جديدة.
- تم تحديث اختبارات الصفحة الرئيسية وiframe وxHamster لتتأكد من ظهور صيغ المحتوى أثناء الإعلان، مع بقاء روابط الإعلان وبيانات المقاطع القديمة مستبعدة.

هذه التعديلات تصلح منطق الالتقاط وإعادة المحاولة في المصدر، لكنها لا تثبت أن كل رابط CDN سيقبل الطلب؛ أخطاء HTTP 410 أو رفض الجلسة يجب تأكيدها على الجهاز بعد البناء.

## الإصدار 1.11.7 — تكامل yt-dlp الفعلي

أضيف اعتماد Android الرسمي من مشروع `yausername/youtubedl-android`:

- Maven: `io.github.junkfood02.youtubedl-android:library:0.18.1`.
- محرك yt-dlp يعمل داخل التطبيق عبر Python وQuickJS المرفقين بالمكتبة.
- يبدأ استخراج صفحة الفيديو من `onPageFinished` للمسارات المعروفة كصفحات فيديو (ومنها xHamster وPornhub) قبل ضغط Play.
- يمرر `User-Agent` و`Referer` و`Origin` وCookie من Android `CookieManager` إلى طلب الاستخراج. لا تحفظ Cookies أو Authorization في قائمة التنزيلات أو التشخيص.
- تُدمج الصيغ المكتشفة بواسطة yt-dlp مع مصادر WebView/HLS الموجودة، مع إزالة الروابط المتطابقة فقط؛ تبقى الجودات المتساوية ذات الروابط/الترميزات المختلفة.
- يبقى التقاط WebView مسارًا احتياطيًا، ولا يغيّر لون الزر العائم أو شرط رصد التشغيل الفعلي.
- لا تعرض هذه النسخة صيغ MPEG-DASH (MPD) أو Video-only/Audio-only المنفصلة؛ لأن DownloadCenter الحالي لا يملك بعد مسار دمج DASH. كما لا تعرض روابط لا تتعرف عليها قائمة التنزيل الحالية.
- من الإعدادات يمكن فحص وتحديث yt-dlp إلى إصدار Stable. لا يتم تنزيل محرك جديد تلقائيًا في الخلفية.

### القيود والتوافق

حزمة الاختبار مضبوطة حاليًا لـ `arm64-v8a` لتقليل حجم مكونات Python/QuickJS المضمنة، وموجهة إلى جهاز ARM64. تحتاج أول تهيئة للمكتبة إلى اتصال إنترنت، كما يحتاج تحديث yt-dlp اليدوي إلى اتصال بمستودع GitHub. ينفّذ yt-dlp استخراج الصفحة مباشرة قبل التشغيل، لكن صلاحية كل رابط تعتمد على استجابة الموقع والجلسة؛ ولا يضمن وجود كل جودة لكل فيديو.

### بناء APK التجريبي

يتضمن المصدر GitHub Actions workflow باسم `Build APK`. ارفع محتويات الحزمة إلى مستودعك، ثم افتح `Actions` واختر `Build APK` واضغط `Run workflow`. بعد نجاح البناء نزّل artifact باسم `VideoBrowser-APK` وثبّت APK الناتج. الحزمة المصدرية هنا ليست APK مبنيًا؛ لم يُنفذ `assembleDebug` في بيئة إعدادها لعدم توفر Android SDK/Gradle واتصال تنزيل الاعتماديات.
